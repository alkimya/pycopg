<objective>
F04 (ETL-INC-F04): let a user serialize concurrent runs of the same pipeline via a PostgreSQL advisory
lock. Opt-in `Pipeline.concurrency: Literal["wait","skip"] | None = None` (D-12), available to ALL
pipelines (concurrent `replace`/`append` race too, though incremental is the motivation).
`"wait"` → `pg_advisory_lock` (block until the peer finishes → serialize); `"skip"` →
`pg_try_advisory_lock`, and if the lock is already held return a transient
`RunResult(status="skipped", run_id=None, ...)` writing NO `pipeline_runs` row (mirrors `dry_run`,
D-13). The lock is SESSION-scoped on a dedicated connection held for the entire run span and released
in a `finally` — connection close auto-releases even on crash (D-14). The key is derived server-side
via `hashtextextended(%s, 0)` with the pipeline name BOUND as `%s` (D-15) — never a
`PYTHONHASHSEED`-salted `hash()`, never interpolated.

Purpose: prevent overlapping runs corrupting the watermark race (a transaction-scoped lock is
insufficient — it leaves the watermark-read/extract race open, so D-14 mandates session scope). Opt-in
default `None` = byte-identical to today (no extra round-trip).

Output: three `ETL_ADVISORY_*` constants in `queries.py`; `Pipeline.concurrency` field + guard; the
lock acquire/finally-release wrap in both `run()` methods (outermost, dry_run bypassed); the
`'skipped'` transient status (RunResult docstring updated, no CHECK-constraint change). New
`tests/test_etl.py::TestAdvisoryLock` with a live two-connection held-lock integration test. Both
`run()` occurrences edited in one commit (C-04).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| consuming app → Pipeline(concurrency=) + pipeline.name | The pipeline name becomes the advisory-lock key source; concurrency is a bounded Literal |
| run() → dedicated lock connection → PostgreSQL pg_advisory_lock | The mutual-exclusion primitive; must be server-side + deterministic across processes |
| lock lifecycle (acquire → run span → finally release / connection close) | An unreleased lock is a DoS surface |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-49-05-01 | Tampering | pipeline name used as the advisory-lock key | mitigate | Name ALWAYS bound as `%s` into `hashtextextended(%s, 0)` — never string-interpolated (D-15); name-bind injection unit test asserts the constants contain no name text. |
| T-49-05-02 | Spoofing / Correctness | non-deterministic lock key defeating cross-process serialization | mitigate | Key derived server-side via `hashtextextended` — NOT a Python `hash()` (PYTHONHASHSEED-salted → per-process key → lock never serializes); rejected explicitly (D-15, RESEARCH Don't-Hand-Roll). |
| T-49-05-03 | Denial of Service | orphaned advisory lock from a crashed/killed run holding it forever | mitigate | Session-scoped lock on a dedicated connection released in `finally` + PostgreSQL auto-release on connection close for ANY reason (verified live, RESEARCH §F04); crash-path integration test proves release. |
| T-49-05-04 | Denial of Service | transaction-scoped lock leaving the watermark-read/extract race open | mitigate | Use SESSION-scoped `pg_advisory_lock`/`pg_try_advisory_lock` spanning before `_read_watermark` through `_end_run`, NOT `pg_advisory_xact_lock` (Pitfall 1). |
| T-49-05-05 | Tampering | 'skipped' transient status corrupting run-log state | mitigate | `"skip"`-when-held writes NO `pipeline_runs` row (mirrors `dry_run`); the `status` CHECK constraint is unchanged; integration test asserts no row is written (D-13). |
| T-49-SC | Tampering | npm/pip/cargo installs | accept | Zero new runtime/dev dependencies — every function (`pg_advisory_lock`/`pg_try_advisory_lock`/`pg_advisory_unlock`/`hashtextextended`) is a core `pg_catalog` built-in (RESEARCH Package Legitimacy Audit: N/A). |
</threat_model>
