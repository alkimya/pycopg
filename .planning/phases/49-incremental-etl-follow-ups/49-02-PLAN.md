<objective>
F02 (ETL-INC-F02): let a user configure the incremental boundary — inclusive `>=` and/or a lookback
overlap — instead of the fixed exclusive `>`. Two orthogonal keyword-only `Pipeline` fields
(`incremental_inclusive: bool = False`, `incremental_lookback: timedelta | int | None = None`, D-05).
The lookback is subtracted in Python before binding (D-06); the RECORDED watermark is always the true
`max(col)` — lookback only widens the read window, never regresses the stored value (D-07).

Purpose: production ETL often needs late-arriving-data overlap (lookback) or boundary-inclusive
re-reads; both are safe because incremental requires `load_mode="upsert"` (C-01) — the overlap replay
is an idempotent ON CONFLICT no-op (D-08). Default `(False, None)` reproduces today's exact SQL.

Output: two new frozen `Pipeline` fields; `_build_incremental_extract_sql` gains an `inclusive` param;
`_do_extract` threads it (sync+async); `run()` computes the lookback-adjusted read floor with a
runtime `ETLError` guard for str-watermark+lookback (sync+async, same commit — C-04). Extended
`tests/test_etl.py::TestBuildIncrementalExtractSql` + a live-DB floor/record-divergence test.
