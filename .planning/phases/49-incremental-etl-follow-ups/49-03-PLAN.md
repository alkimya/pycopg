F03 (ETL-INC-F03) — PURE LAYER: let a user declare a composite (multi-column) incremental watermark
key. This plan delivers the non-`run()` surfaces: widen `incremental_column` to
`str | Sequence[str] | None` normalized to a tuple (D-09); extend `_build_incremental_extract_sql`
with the native Postgres row-value comparison `WHERE (c1, c2) > (%s, %s)` (D-10); add the new
`"composite"` envelope tag to `_encode_watermark`/`_decode_watermark` reusing the frozen per-scalar
codec element-wise (D-11, C-02); and validate a composite `initial_watermark` as a matching-length
sequence (D-04). The `run()` wiring (composite max-ROW capture, extract named-bind reconciliation,
persist) lands in the follow-on plan 49-04.

Purpose: composite touches the most surfaces; splitting the pure/testable layer (SQL builder + codec
+ construction guards, all unit-testable without `run()`) from the ~280-line duplicated `run()`
wiring keeps each plan within budget and keeps quality high. Single-column pipelines stay
byte-identical (zero migration — old JSONB rows decode exactly as before, C-02).

Output: widened field + tuple normalization + D-04 guard; composite builder branch; composite codec
tag; `tests/test_etl.py::TestCompositeWatermark` (SQL-shape, envelope round-trip, single-column
regression, injection, construction guards). Both accessors' shared pure functions edited in one
commit (C-04).

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-49-03-01 | Tampering | composite column name injected into `(c1, c2) > (...)` | mitigate | `validate_identifiers(*column)` over EVERY composite element as line 1 of `_build_incremental_extract_sql` before any string interpolation (D-10); dedicated composite-injection test (`("day","se q")` → InvalidIdentifierError). |

| T-49-SC | Tampering | npm/pip/cargo installs | accept | Zero new dependencies this plan — supply-chain surface unchanged. |
