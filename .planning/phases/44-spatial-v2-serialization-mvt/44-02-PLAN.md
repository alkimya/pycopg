<objective>
Add `as_mvt` (SPAT2-12) — the critical-path serialization method — to
`db.spatial.*` and `async_db.spatial.*`. Unlike the scalar serializers it has a
unique subquery SQL shape, a unique return type (`bytes`), its own dedicated
builder (`build_mvt_sql`) and its own dedicated runner (`_run_mvt`/`_arun_mvt`)
that bypasses `_run` entirely. The builder always emits the enforced
`ST_Transform → ST_AsMVTGeom → ST_AsMVT` pipeline; the runner always returns
`bytes` (`b""` for an empty tile).

Purpose: A real `/tiles/{z}/{x}/{y}.mvt` endpoint can be built without raw SQL —
MVT is the milestone differentiator. The pipeline is enforced (criterion #2) and
proven by decoding the returned bytes to the expected feature count, not merely
`isinstance(result, bytes)`.

Output: `build_mvt_sql` builder, `_run_mvt`/`_arun_mvt` runners, `as_mvt` on both
accessor classes, the SQL-shape + multi-arg injection + bytes-coercion routing
tests, a dependency-free pure-Python MVT decoder test helper, and live
decode-to-feature-count + empty-tile-`b""` integration tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller → `build_mvt_sql` | `table`/`schema`/`geom`/`columns`/`feature_id_column` are caller-supplied identifiers; `feature_id_column` is interpolated as a literal SQL identifier (PostGIS requires the column name in the query text, not a bind) |
| caller → `build_mvt_sql` numerics | `tile_z`/`tile_x`/`tile_y`/`extent`/`srid` are numeric literals interpolated into the SQL via `int()` |
| caller → `as_mvt` | `filter` is a raw SQL fragment (born-clean documented escape hatch); `layer_name` is a `%s` bind |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-44-02 | Tampering (SQL injection via identifiers) | `build_mvt_sql` (`table`/`schema`/`geom`/`columns`/`feature_id_column`) | mitigate | `validate_identifiers(table, schema, geom)` is line 1; `validate_identifiers(*columns)` and `validate_identifiers(feature_id_column)` follow before any interpolation. `feature_id_column` is interpolated ONLY after passing the guard. Verified by `TestBuildMvtSql` injection tests asserting `InvalidIdentifierError` for each of the four identifier paths before SQL is sent |
| T-44-02b | Tampering (injection via numeric tile/extent/srid args) | `tile_z`/`tile_x`/`tile_y`/`extent`/`srid` | mitigate | All coerced via `int()` before interpolation (the P43 `build_extent_sql` `int(srid)` precedent) — a non-integer raises `ValueError`/`TypeError`, no string reaches the SQL text; `layer_name`/`extent` also bound as `%s` |
| T-44-02c | Information disclosure via `filter=` raw fragment | `as_mvt` `filter` (inner subquery WHERE) | accept | `filter` is a documented raw-SQL escape hatch consistent with the spatial surface; caller owns the fragment; no identifier path bypasses the line-1 guard |
| T-44-02d | Denial of service (pathological tile / huge extent) | `extent`/tile coords | accept | Bounded by PostGIS execution; `int()` coercion prevents non-numeric abuse; tile servers already gate z/x/y ranges at the HTTP layer (out of library scope) |
</threat_model>
