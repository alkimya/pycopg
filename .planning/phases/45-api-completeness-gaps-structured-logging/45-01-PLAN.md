<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| application → `get_logger()` / `log_operation` | the application owns the handler stack; the library only attaches a `NullHandler` and emits records |
| operation name / `rows` → log record `extra` | values placed into `extra={}` are emitted to whatever handler the app attaches |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-45-01 | Information disclosure (sensitive data in logs) | `log_operation` `extra` fields | mitigate | `log_operation` records only an operation *name* (caller-chosen constant string), a numeric `duration_ms`, and an optional integer `rows` count — never SQL text, parameter values, DSNs, or credentials. No connection object or query string is passed to `extra`. Verified by `test_log_operation_extra` asserting only `operation`/`duration_ms`/`rows` keys. |
| T-45-02 | Tampering / unexpected side effects on the app's logging config | module import | mitigate | The module attaches ONLY a `logging.NullHandler` to the `pycopg` logger and NEVER calls `logging.basicConfig()` — it cannot hijack or reconfigure the root logger or the app's handlers (library rule, D-08). |

No `high`-severity threats. Both surfaces are information-disclosure-class and fully mitigated by construction.
</threat_model>
