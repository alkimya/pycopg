<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local commit -> git tag | The annotated tag must sit on the exact gates-green, version-1.2.0 commit — a wrong-commit tag ships mislabeled code |
| GitHub Release -> PyPI (OIDC) | The `release: published` event authorizes a trusted-publisher upload with no long-lived token; the human creating the Release is the go/no-go gate |
| PyPI wheel -> local smoke | The installed wheel must self-report 1.2.0; a repo-root import can shadow it and mask a bad artifact |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-54-07 | Tampering | tag/wheel version mismatch (tag on wrong commit, or PyPI wheel != 1.2.0) | mitigate | Task 1 asserts the tag points at the commit where pyproject reads `version = "1.2.0"` and re-runs all 5 gates first; Task 3's clean-venv smoke asserts the INSTALLED wheel's `__version__ == "1.2.0"` and that `__file__` is inside site-packages (not the repo), catching source-shadowing false passes |
| T-54-08 | Elevation of Privilege / Spoofing | OIDC publish integrity (unauthorized or accidental publish) | mitigate | Publish only via GitHub OIDC trusted publisher (no stored token), triggered solely by a human-created GitHub Release (blocking checkpoint); publish.yml runs `uv lock --check` before `uv build`, refusing a mismatched lockfile |
| T-54-09 | Tampering | supply-chain: the smoke `pip install` pulling an unexpected/typosquat artifact | mitigate | The smoke pins the exact `pycopg==1.2.0` from PyPI (our own just-published trusted-publisher artifact) and asserts version + install location; no NEW third-party dependency is added anywhere in this phase (vulture was already a dev-dep), so there is no new package-legitimacy surface to audit |
</threat_model>
